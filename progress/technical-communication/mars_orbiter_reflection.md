# Mars Climate Orbiter Interlude Reflection

## Reflection Questions

1. **Implicit assumptions in my Module 2 document:**
   - Assumed Priya knows what "API" means (didn't define it)
   - Assumed Priya knows what "migration" means in software context
   - Assumed "frontend" means the user-facing part of the application (defined it, but could be clearer)
   - Assumed Priya has access to Confluence and Slack (didn't mention if she needs accounts)
   - Assumed the migration timeline is fixed at 8 weeks (didn't mention it could shift)

2. **Specifications I've assumed are clear but never verified:**
   - API contract definitions in previous projects - assumed the consuming team interpreted them the same way we wrote them
   - Database schema changes - assumed other teams understood the impact without explicit migration guides
   - Environment variable configurations - assumed the naming conventions were "obvious"
   - Error message formats - assumed the error codes were self-explanatory without user testing

3. **Deciding which clarifications are worth making:**
   - The Mars Climate Orbiter teaches that the cost of ambiguity is often invisible until it causes failure. A "trivial" clarification that takes 4 words to write can prevent a catastrophic failure. I should ask: "What is the worst-case cost if this is misunderstood?" If the cost is significant (data loss, money, time), the clarification is worth making regardless of how "obvious" it seems.

## Four Words Missing From My Document

"API (Application Programming Interface) - a set of rules for how software components communicate"

This four-word addition would make the term explicit for a new engineer who might not know what API means, just as "newton-seconds" would have saved the Mars Climate Orbiter.
